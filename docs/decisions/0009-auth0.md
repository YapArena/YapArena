# Decision 0009 — Auth0 replaces Privy

Status: approved by the founder, 2026-10-23. Supersedes the Privy-specific parts of
[Decision 0008](0008-auth-simplification.md) and [embedded wallets](../history/embedded-wallets.md);
keeps 0008's application-authoritative session model.

## Why

- YC is an internal ledger. Purchases go through a payment provider and future withdrawals go to a
  user-supplied external address, so no flow needs an embedded wallet. The Privy wallet holds no value.
- Identity held both at Privy and in YapArena caused the freeze, re-check and repair machinery.
- The founder does not want to own credential security, which rules out a self-hosted library.
  Privy wallets with custom auth require Privy Enterprise.
- Auth0's Free plan covers 25,000 monthly active users. With no stored passwords, leaving Auth0 later
  needs no password-hash export.

## Target model

    "Sign in" link → GET /api/auth/login?return=<path>
      → Auth0 Universal Login (Identifier First: email code, or Google) → GET /api/auth/callback
      → verify ID token, map (auth0, sub) → account → __Host-session (opaque, 7 days, authoritative)
    Each request: one SELECT on sessions and users. No Auth0 call.

1. **Protocol.** OpenID Connect authorization code flow with PKCE (S256), state and nonce, as a
   confidential Regular Web Application, using an exact-pinned `openid-client`. No Auth0 browser SDK
   and no React. State, nonce, PKCE verifier, return path and purpose are stored server-side for
   10 minutes and consumed once; a `__Host-` cookie binds them to the browser.
2. **Sign-in methods.** Email one-time code (Auth0 Passwordless Email connection) and Google. No
   passwords, passkeys, other social or wallet sign-in for now.
3. **Identity.** Each `(provider 'auth0', subject = ID token sub)` maps to exactly one account; an
   account may have several subjects (one per method). The callback requires `email_verified`,
   stores an email snapshot and respects the signup pause. Return paths are same-origin relative
   paths only.
4. **Linking Google and email (verified at sign-in).** Accounts are never merged on email alone.
   - A new subject whose verified email matches no account creates an account.
   - A Google sign-in with an unknown subject whose email matches an existing account does not
     create an account or a session. The server stores a one-use, 10-minute pending link
     (Google subject, account, email) and sends the browser through the email-code connection
     with `login_hint` set to that email and `prompt=login`. When that callback returns a verified
     email-code identity for the same email that belongs to, or is then attached to, the same
     account, the Google subject is attached and the user is signed in. Abandoning the code
     leaves nothing linked.
   - An email-code sign-in with an unknown subject whose email matches an account created through
     Google is itself proof of the mailbox: the email subject is attached and the user signed in.
   - Email matches with more than one account, a suspended account or an unverified email are
     refused with a support message. Each link writes an audit event and an in-app notice. There
     is no unlink UI for now.
5. **Session.** The callback rotates into a new `__Host-session` (7-day absolute lifetime). No
   periodic provider re-check, webhook or log stream.
6. **Sign out** deletes this device's session row, then redirects to Auth0's logout endpoint with a
   return to the site. It ends this device only (founder, 2026-10-22).
7. **Authority.** YapArena owns suspension and deletion. Blocking or deleting a user in the Auth0
   dashboard is not relied on to end sessions; the incident runbook suspends in YapArena first.
8. **Confirmation (step-up).** A sensitive operation creates a one-use, five-minute challenge bound
   to the account and operation. The browser goes through Auth0 again with `prompt=login` and
   `max_age=0`; the callback requires a subject of the same account, matching state/nonce and an
   `auth_time` at or after the challenge's creation. This replaces the Privy passkey proof in
   `account_operations` and the sandbox "strong method" check. The founder accepts that real
   withdrawals may open with this confirmation alone, so a mailbox or Google takeover can request a
   withdrawal. Until a stronger factor exists, real withdrawals keep these safeguards: the approved
   manual review before payout, an email and in-app notice for each withdrawal request and each new
   destination address, and a 24-hour wait before a new destination address can be used. A stronger
   factor (passkey or MFA, possibly a paid Auth0 plan) is added after real withdrawals open; it is
   not a financial-activation gate.
   _Amended 2026-10-25 by [Decision 0013](0013-yap-coins-always-on-and-debate-staking.md):
   opening the coin sandbox no longer needs a confirmation, because Yap Coins are always on.
   Withdrawals and recovery consents keep it._
9. **No embedded wallet.** Provisioning ends. Future withdrawals go to a user-supplied address
   confirmed per point 8.
10. **Tests and local development.** 0008 point 7's test identity entry is kept: it calls the same
    post-callback sign-in function, lives under `scripts/`, never ships and keeps its startup
    refusals. The callback is tested against an in-process OIDC issuer with real signatures.
11. **Tenants and secrets.** Separate staging and production tenants; production uses a custom
    domain (the production service refuses an `*.auth0.com` issuer), its own email provider and
    its own Google OAuth client. The privacy policy names Auth0 and Google and the data region.
    Auth0 sign-in settings live on the web service only; the deletion credential lives only on the
    jobs worker.
12. **Existing accounts.** Privy-linked staging accounts are not migrated; staging is reset before
    the Auth0 release. No mapping from Privy by email.
13. **Account deletion.** A signed-in user can delete their account after a confirmation per
    point 8. YapArena ends every session, marks the account deleted, removes its sign-in subjects
    and erases personal data under the retention rules below, then a durable jobs-worker task
    deletes each linked Auth0 user through the Management API (credential limited to
    `delete:users`; 404 counts as done; bounded retries, then review). The Auth0 call never blocks
    or undoes the local deletion. Retention rules: <founder decisions from Prompt 12c>.

## Risks

| Risk                                                                          | Mitigation                                                                                     |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Auth0 outage blocks new sign-ins and confirmations                            | Existing sessions, browsing and debating continue                                              |
| Email or Google compromise can request a withdrawal (accepted by the founder) | Manual review, notices and the 24-hour new-address wait (point 8); stronger factor added later |
| Linking bug merges the wrong accounts                                         | Linking only after a verified email code (point 4); tests cover every branch                   |
| Dashboard block does not end live sessions                                    | Suspend in YapArena; sessions end within 7 days at most                                        |
| Data stored outside Canada (region unconfirmed)                               | Disclose in the privacy policy; review before production                                       |

## Supersedes in 0008

Privy target model and points 1–3, 5 and 6 where they name Privy; "Privy facts used"; rollout
rows 11–12; open questions 1 and 3. Kept: authoritative app session, single-device sign-out, test
entry, release-compatible expand/contract migrations, `account_status`, signup pause and Redis limits.
