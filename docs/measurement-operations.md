# Product measurement and operating review

## Data contract

Measurement is the analytics cookie in the cookie banner (founder, 2026-10-30; see `/cookies`). It is off until a browser chooses **Accept all** or turns on **Analytics** in **Cookie settings**; **Reject all** and **Accept all** have the same weight. The browser receives a random, HttpOnly, same-site cookie; the database stores only its SHA-256 digest. The optional browser choice is separate from the account session. Turning Analytics off in **Cookie settings** (footer, or the account Privacy tab) deletes the consent row and cascades to that browser's events and watch sessions. The server rejects browser measurement without active consent. Account actions are recorded only after the action succeeds and only when the acting request carries consent. Telemetry failure cannot fail the product action.

Raw measurement does not contain email, handle, wallet address, IP address, chat/report text, search terms, or URL query strings. Internal account, debate, and topic IDs enable reviewed affiliation and different-content returns; none are Prometheus labels. A wallet is never used as a unique-person key. Demo content is excluded. The public completion event has no browser or account ID and is written by the authoritative live-end transition. This is a count of completed debates, not a participant count or result.

| Event              | Trigger and unit                                                                                                                                                        | Deduplication / qualification                                                                                                                                                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `discovery_view`   | Consented browser opens home, list, match, profile, or published non-demo topic/debate page                                                                             | Once per browser, surface, target, UTC day. Profile discovery has no profile identifier.                                                                                                                                                 |
| `match_requested`  | A signed-in, consented account successfully creates a request                                                                                                           | One event for the created request.                                                                                                                                                                                                       |
| `match_accepted`   | A signed-in, consented account successfully accepts a request or joins a queue match                                                                                    | One event for the resulting event.                                                                                                                                                                                                       |
| `debate_completed` | A published non-demo debate first gets `live_ended_at`                                                                                                                  | Unique debate ID; recorded without browser consent or identity because this is event state. It says nothing about a winner.                                                                                                              |
| `replay_started`   | A consented browser begins a watch session for a published ready replay                                                                                                 | Once per accepted watch session, not on every heartbeat.                                                                                                                                                                                 |
| `follow_created`   | A signed-in, consented account creates a follow                                                                                                                         | Successful creations only; idempotent repeats do not increment.                                                                                                                                                                          |
| `report_submitted` | A signed-in, consented account creates a private moderation case                                                                                                        | Successful creations only; no reason or report text in product events.                                                                                                                                                                   |

This is a return **visit**, not yet the PRD's engaged participant metric.                                                                                                                          |
| Watch seconds      | Live video or replay is playing in a visible tab with consent; browser starts a UUID session and sends progress every 10 seconds                                        | Server computes elapsed time, caps each increment at 30 seconds and session total at 4 hours, and refuses ended, expired, duplicate, or wrong-browser sessions. This measures playback indication, not media quality or a unique person. |

Raw events and watch sessions are deleted after 90 days. Unused consent rows expire after 180 days; affiliation review audit entries after 365 days. Withdrawal deletes the browser's raw measurement immediately. Daily retention runs in the app maintenance clock and logs errors without stopping the server. Database backups can retain older deleted rows until their configured backup expiry; apply the backup retention policy separately. A previously exported aggregate cannot be retracted, so avoid exporting small-cell person-level reports.

`/measurement` and `/api/measurement/dashboard` are operator-only. The dashboard and the separate `yaparena-product` Grafana board aggregate the trailing 28 days. They show discovery, match, completion, live/replay watch, follows, reports, and return visits by **reviewed** founder-affiliated, independent, or unclassified activity. A trained operator assigns account affiliation by published profile handle and a reason; each change has an internal audit entry. Anonymous activity and unreviewed accounts remain unclassified. A completion is founder-affiliated if any speaker is classified founder, independent only if both speakers are reviewed independent, otherwise unclassified. These categories may change after review. No label contains a person, URL, wallet, debate, topic, case, or token. The existing HTTP health board remains separate.

## 28-day returning participant metric — definition approved, gate pending

The product owner approved this **definition only** on 2026-10-02: each UTC-day cohort contains consented accounts reviewed as independent whose engagement on a published non-demo debate reached at least 10 measured live/replay watch minutes **or** a completed debater appearance. The numerator is those same accounts that meet the engagement rule on a **different debate or topic** within the following 28 complete UTC days. Calculate the cohort rate as numerator / denominator after its full observation window; show cohort sizes, watch and debater sources, missing-consent coverage, and confidence intervals. Count accounts, not wallets or sessions. Exclude founder-affiliated, unclassified, deleted-consent, and demo activity from both sides. Financial actions from the PRD are omitted because they do not exist. The PRD's 30% hypothesis remains **unapproved** and is not a launch or success gate. The current event store captures the needed watch sessions and completion state, but does **not** publish this rate yet: retroactive consent withdrawal and affiliation review need a cohort materialization policy before it is a stable gate. Product owner approval of the threshold, minimum sample, and treatment of consent withdrawal is required before any gate is configured.

## Release and rollback sequence

1. Record branch, commit, UTC time, Render deploy ID, and a named operator. Review the migration and take a provider backup or snapshot with the provider's documented restore window. Verify backup access in a separate database or project; a downloaded archive list is insufficient.
2. Apply pending migrations once in the separate owner operator/job process, then manually deploy the matching reviewed app commit/image. Follow the [staging deployment sequence](render-staging.md#deploy-the-web-service); startup only verifies runtime identity and migration currency and never migrates. Keep owner/admin credentials out of web and worker environments. Confirm migration ID and `/ready`; run `SMOKE_BASE_URL=https://<host> node scripts/smoke-staging.ts` from an allowed network, then browser and operator journeys. Keep credentials out of logs.
3. Check `/metrics` and the separate Grafana product board for `yaparena_product_snapshot_fresh=1`; a zero means the aggregate query failed. Compare a small known, consented synthetic event against the operator dashboard, then withdraw consent and verify removal. Remove synthetic accounts and content.
4. If code fails, stop the deploy and restore the prior known-good commit only after confirming old code accepts the new additive schema. Do not run the migration `down` on a database with new measurement rows: it drops them. A forward fix is preferred. Restore the backup into an isolated database first for corruption or loss; do not overwrite the live database as a normal code rollback. Record the incident timeline and repeat smoke checks.

For a local disposable database, `BACKUP_VERIFY_LOCAL=1 bash scripts/verify-backup-restore.sh` takes a custom-format archive, restores to a new database, compares measurement row counts, checks the migration record, and removes the temporary archive and database. CI runs this. Provider backup/restore, retention configuration, and credentials need a separate staging verification; CI does not prove them.
